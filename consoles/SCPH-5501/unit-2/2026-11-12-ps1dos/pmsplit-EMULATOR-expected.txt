console-v31-split: where the 386 core's time goes, phase by phase, to lay a console beside the emulator (main,
2026-11-13: v30's pm386 ran 0.40-0.48% more cycles on the 5501 and the PSone than on the emulator, identical on
both consoles, while con386 agreed to 0.004%). tests/pmsplit.c runs tests/pm/split.asm (16 phases between OUT EAh
markers; its log matches Bochs's, 18 lines) and times each phase on Timer 2. Both hand the console back.

pmsplit.exe (aa7e7c12): the core built -O2, as pm386.exe's.  pmsplit-os.exe (27aff7a9): the core built -Os, as
con386.exe's. The same C, two layouts: a gap that follows the build is the code's (where it falls in the I-cache,
its calls); one that follows a phase is that phase's work (RAM spread, page walks, table loads, gates, V86).

Found already, on the emulator: this core's speed is its I-cache layout. Changing pmsplit.c alone (a few hundred
bytes, before the core in the link) moved phase 1 of the -O2 build from 1509.5 to 1532.7 cycles an instruction.

The instruction counts and the 18 log lines must be the same on a console (they are the core's, not timing). Each
phase's console/emulator cycle ratio is the finding: the same ~1.0045 everywhere in the -O2 run and ~1.0000 in the
-Os one would put the gap in how the emulator charges this layout's code (I-cache refills, or the 0.47% call-bench
pattern); a ratio that stands out in one phase points at that phase's work. Each run is ~16 s (-O2) / ~19 s (-Os).
